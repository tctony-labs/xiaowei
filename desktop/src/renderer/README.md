# Renderer UI 开发

本文约定 renderer 的组件边界、Storybook 开发流程及 UI 验收要求。具体组件的场景以相邻 Storybook 文件为准，设计取舍和验收状态维护在对应事项文档中。

## 组件与业务边界

- 展示组件通过 props 接收数据，通过回调通知外层；Electron IPC、Rust 调用和网络请求留在页面适配层。
- 产品与 Storybook 复用同一组件及全局样式，组件与 `.stories.tsx` 放在一起。
- 预览使用固定模拟数据，不执行真实业务操作；模拟状态应覆盖本次需求，不创建无意义的场景。

## 样式与主题

- 设计变量统一维护在 renderer 全局样式中，产品与 Storybook 使用同一份定义。
- 组件使用语义颜色变量及对应类名，不自行硬编码品牌色或另选颜色。品牌主色与普通文字的可读性用色分开，例如普通字号的绿色文字使用 `text-primary-text`；具体色值以样式源码为准。
- 全局样式移除默认 focus outline，但保留焦点行为；组件负责选中与焦点的视觉表达，并覆盖键盘操作场景。

## 视觉变更与确认

Storybook 的人工确认主要用于 UI 视觉效果。新增、迁移 UI 或修改布局、样式、状态展示等视觉效果时，先在 Storybook 中实现并展示本次范围内的 UI 状态及相关交互。

- 迁移已有功能时，对齐原有 UI 样式、状态展示和交互，不自行重新设计。
- 新增功能时，根据需求设计并展示组件效果、状态和交互。

上述视觉效果必须由用户确认后，才能接入项目的实际页面和业务逻辑。不得先接入项目再补 Storybook，或未经确认直接接入。修改已接入的共享组件的视觉效果时，确认前不得让未确认的视觉改动直接生效于产品页面。

无视觉变化且预期明确的行为修复可直接实施并验证，无需额外的 Storybook 人工确认。例如，复制新内容后自动选中最新条目属于选中行为修复，不因选中状态切换而视为视觉设计变更。使用 Storybook 验证交互不自动触发人工确认。

## 开发与验收流程

1. 明确本次范围和状态清单。迁移已有功能时，在对应事项或说明文档中记录原有表现和明确调整，不为此强制新建 record。
2. 按组件与业务边界实现 UI，以模拟数据展示空内容、有内容、长文本、明暗主题及相关加载和错误状态；按实际需求选择场景。
3. 在 Storybook 中检查视觉效果，对照基准时固定视口、主题和字体环境。仅经用户确认的视觉结果才可成为新基线。
4. 按需增加组件交互测试；Storybook 的 `play` 可用于呈现指定视觉状态，纯流程测试放在相邻测试文件中。
5. 视觉确认后接入实际页面与业务逻辑，在 Electron 中验收平台行为。

正常启动、构建和测试流程由对应配置与脚本维护，具体命令和参数以脚本为准。Storybook 可独立启动，不等于桌面冷启动；桌面启动与重启遵循 [AGENTS.md 的运行实例规则](../../../AGENTS.md#运行实例)。

## 验证边界与易错点

- 构建或测试通过不能代替视觉验收，浏览器预览不能代替 Electron 平台行为验收。
- 普通键盘模拟或合成组合输入事件不能替代真实输入法验收；需要人工检查的输入法和平台行为应明确记录。
- 浏览器中触发窗口、文件或系统操作的回调，只能证明交互通知正确，真实效果仍需在桌面验证。
- 共享组件的修改可能同时影响 Storybook 与产品，必须确保视觉确认前的改动不直接生效于产品页面。

## Gateway 业务调用

- 业务调用统一使用 [services.ts](src/services.ts) 的 typed service 入口，通过 preload 暴露的 `window.gateway` 连接；展示组件不直接建立连接或新增业务 IPC。
- 每个 renderer 按需创建一个共享 client，每个 service 首次使用时绑定并缓存；导入模块不建立 Electron 连接。
- Storybook 和测试通过 `createServices(connect)` 注入独立 client，避免使用真实桌面连接或在不同预览之间共享业务状态。

### 异步调用易错点

- 页面通过“事件订阅 + 初始快照”保持数据同步时，先等待订阅 ready，再读取首轮快照，避免漏掉订阅建立期间的变化。
- 订阅可能在组件卸载后才建立；此时须关闭迟到订阅，避免泄漏和卸载后的状态更新。
- 对顺序敏感的调用（例如窗口布局更新）应按序执行，避免异步完成顺序覆盖最新状态；异步调用须处理 Promise 错误。
