# Renderer UI 开发

本文约定 renderer 的组件边界、Storybook 开发流程及 UI 验收要求。具体组件的场景以相邻 Storybook 文件为准，设计取舍和验收状态维护在对应事项文档中。

## 组件与业务边界

- 展示组件通过 props 接收数据，通过回调通知外层；Electron IPC、Rust 调用和网络请求留在页面适配层。
- 产品与 Storybook 复用同一组件及全局样式，组件与 `.stories.tsx` 放在一起。
- 预览使用固定模拟数据，不执行真实业务操作；模拟状态应覆盖本次需求，不创建无意义的场景。

## React 热更新边界

- 产品组件模块只导出 React 组件和 TypeScript 类型。共享函数、hooks、数组及对象数据放到职责明确的普通 `.ts` 模块；不要从组件文件重新导出这些值。Vite 支持的字符串／数字等常量可保留。
- `src/main.tsx` 只负责一次性入口副作用和 `createRoot(...).render(<App />)`，不在入口声明 React 组件。根组件放在 `src/App.tsx`，主题操作放在 `src/theme.ts`。
- 根 Biome 配置对产品 TSX 启用 `useComponentExportOnlyModules`（error，允许 Vite 常量导出），由常规 check／提交检查拦截混合导出。Storybook 场景和测试不作为产品 Fast Refresh 边界，排除此规则。
- 修改组件应由 Fast Refresh 更新现有树，不应再次输出 `Renderer starting` 或出现重复 `createRoot()`。普通模块或入口变化可以退回整页重载；重载后须验证设置加载、事件订阅和存储统计，而不只看页面是否显示。
- 热更新不等于新建 document，不能通过重新连接 Gateway 或无限重试掩盖生命周期错误。窗口的开发重载策略见 [main README](../main/README.md#开发重载与导航)，会话清理时机见 [Gateway TS](../../../gateway/ts/README.md#electron-接入)。

## 样式与主题

- 设计变量统一维护在 renderer 全局样式中，产品与 Storybook 使用同一份定义。
- 组件使用语义颜色变量及对应类名，不自行硬编码品牌色或另选颜色。品牌主色与普通文字的可读性用色分开，例如普通字号的绿色文字使用 `text-primary-text`；具体色值以样式源码为准。
- 全局样式移除默认 focus outline，但保留焦点行为；组件负责选中与焦点的视觉表达，并覆盖键盘操作场景。

## Storybook 的适用范围与确认

是否需要 Storybook 流程，以本次是否引入新的视觉设计或交互模式为准，不以是否新增功能、组件实例或设置项为准。

以下变更可直接接入产品，无需新增 Storybook 场景或重复视觉确认：

- 复用已有、已确认的组件及展示模式，增加设置项、列表项、菜单项或数据字段。
- 将已有、已确认的 UI 接入真实业务，或开放此前隐藏的已有功能入口，且不改变其视觉设计和交互模式。
- 不改变视觉设计和交互模式的行为修复、数据绑定及状态逻辑调整。

例如，在快捷键设置中复用现有设置行和快捷键录制组件，增加“快速对话”配置，可直接实施并验证。复制新内容后自动选中最新条目属于选中行为修复，不因选中状态切换而视为视觉设计变更。

以下变更需要先在 Storybook 中展示，并经用户确认后接入产品：

- 新增尚未确认的视觉设计或交互模式。
- 修改现有组件的布局、样式、视觉状态或交互呈现。

确认范围仅覆盖本次新增或变化的设计，不要求重复确认沿用部分。复用组件若产生溢出、遮挡等布局问题，需要调整设计时，再按实际变化进入确认流程。迁移已有功能时，对齐原有 UI 样式、状态展示和交互，不自行重新设计。

需要确认的视觉效果必须由用户确认后，才能接入项目的实际页面和业务逻辑。不得先接入项目再补 Storybook，或未经确认直接接入。修改已接入的共享组件的视觉效果时，确认前不得让未确认的视觉改动直接生效于产品页面。

无需视觉确认的变更仍须完成适当的功能验证；使用 Storybook 辅助验证不自动触发用户确认要求。

## 开发与验收流程

1. 明确本次范围和状态清单，按上述适用范围判断是否涉及新的视觉设计或交互模式。无需视觉确认的变更可直接实现并验证，跳过第 2、3 步。迁移已有功能时，在对应事项或说明文档中记录原有表现和明确调整，不为此强制新建 record。
2. 对需要视觉确认的变更，按组件与业务边界实现 Storybook 预览，以模拟数据展示空内容、有内容、长文本、明暗主题及相关加载和错误状态；按实际需求选择场景。
3. 在 Storybook 中检查本次变化的视觉效果，对照基准时固定视口、主题和字体环境，并请用户确认。仅经用户确认的视觉结果才可成为新基线。
4. 按需增加组件交互测试；Storybook 的 `play` 可用于呈现指定视觉状态，纯流程测试放在相邻测试文件中。
5. 接入实际页面与业务逻辑；需要视觉确认的变更须先完成确认。涉及 Electron 平台行为时，在 Electron 中验收。

正常启动、构建和测试流程由对应配置与脚本维护，具体命令和参数以脚本为准。Storybook 可独立启动，不等于桌面冷启动；桌面启动与重启遵循 [AGENTS.md 的运行实例规则](../../../AGENTS.md#运行实例)。

## 验证边界与易错点

- 对需要视觉确认的变更，构建或测试通过不能代替视觉验收；浏览器预览不能代替 Electron 平台行为验收。
- 普通键盘模拟或合成组合输入事件不能替代真实输入法验收；需要人工检查的输入法和平台行为应明确记录。
- 浏览器中触发窗口、文件或系统操作的回调，只能证明交互通知正确，真实效果仍需在桌面验证。
- 共享组件的修改可能同时影响 Storybook 与产品，需要视觉确认的改动在确认前不得直接生效于产品页面。

## Gateway 业务调用

- 业务调用统一使用 [services.ts](src/services.ts) 的 typed service 入口，通过 preload 暴露的 `window.gateway` 连接；展示组件不直接建立连接或新增业务 IPC。
- 每个 renderer 按需创建一个共享 client，每个 service 首次使用时绑定并缓存；导入模块不建立 Electron 连接。
- Storybook 和测试通过 `createServices(connect)` 注入独立 client，避免使用真实桌面连接或在不同预览之间共享业务状态。

### 异步调用易错点

- 页面通过“事件订阅 + 初始快照”保持数据同步时，先等待订阅 ready，再读取首轮快照，避免漏掉订阅建立期间的变化。
- 订阅可能在组件卸载后才建立；此时须关闭迟到订阅，避免泄漏和卸载后的状态更新。
- 对顺序敏感的调用（例如窗口布局更新）应按序执行，避免异步完成顺序覆盖最新状态；异步调用须处理 Promise 错误。
