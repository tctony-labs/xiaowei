# 实施 Plan

`.agent/plans/` 只保存尚在实施且确需落盘的临时计划文件。对话中的简短步骤说明或 Agent 临时任务列表不属于此处的 Plan，不要求转成文件，本约定也不要求进入计划模式。

## 何时创建

默认直接执行并验证；多个步骤、多个文件、常规测试或笼统的“任务复杂”均不单独构成创建 Plan 的理由。仅在以下情形创建：

- 用户明确要求将实施计划保存为文件。
- 确需独立文件支持跨会话恢复或交接，保存后续仍需使用的步骤、依赖和验证检查点。
- 分阶段实施有关键顺序约束、中间状态或验收门槛，简短步骤说明不足以可靠跟踪。

除用户明确要求外，创建前应能用一句话说明需要保存哪些信息、为何现有对话或 record 的 `Current work` 不足；随进度说明即可，无需为选择跟踪方式单独发起确认或等待审批。现有对话或 record 足以跟踪时不再创建 Plan。实施中出现上述需要时再创建，不为已完成的步骤补写 Plan。

Plan 与 record 分别按需启用。没有 record 也可创建 Plan，不得为创建 Plan 或回填结果而擅自新建 record；有关联 record 时，先按 [`records README`](../records/README.md) 确认其处于 `active` 且仍有实施工作，不要求每个切片都有 Plan。

## 组织与内容

有关联 record 时，使用与其主文档文件名词干完全一致的目录；否则使用 `YYYY-MM-DD-kebab-case` 任务目录名。通常一份 Plan 足够，仅在确有独立实施切片时按依赖编号拆分：

```text
.agent/records/active/2026-09-08-dynamic-plugin-loader.md
.agent/plans/2026-09-08-dynamic-plugin-loader/
└── 01-loader-baseline.md
```

内容保持为可执行清单，按需列出：

- 当前切片的目标和完成标准；
- 已知的修改位置、关键依赖和执行顺序；
- 验证方法、必要的人工验收和恢复执行所需的检查点。

不确定的修改位置可在排查后补充，不为填满模板提前设计；不重复事项背景、替代方案和长期架构，已有说明直接链接。

## 完成与清理

无论是否使用 record 或 Plan，都可按需在实施过程中及完成后逐步更新长期文档，不必等到整个事项完成或归档；文档修改遵循根 `AGENTS.md` 的授权规则，同一内容只维护一处。

有关联 record 时，每份 Plan 实施完成后，应立即将持久信息和验证结果回填对应 active record 的 `How` / `Outcome` 或其链接的独立文档，再删除该 Plan，不等整个事项结束；对应目录为空时一并删除。单个 Plan 完成不等于整个事项完成；事项范围完成且不再有基于原事项的重大改动时，按 record 生命周期向用户提议归档，用户明确发起或确认后核对并补齐长期说明，再归档。事项实施完成或离开 `active` 前不得遗留对应 Plan 目录。

没有 record 时，实施时同步更新相关长期文档；完成后按需补齐根 `docs/` 或对应包文档，向用户报告实施结果与验证结论，再删除已完成的 Plan 和空目录，不为回填结果而擅自新建 record。
