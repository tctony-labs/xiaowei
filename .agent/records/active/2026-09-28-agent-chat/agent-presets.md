# Agent Preset：暂缓决定与源码依据

所属事项：[Agent Chat](../2026-09-28-agent-chat.md)。2026-10-10 用户讨论场景预设后确认暂缓 preset，技能后移；当前先集中做好提示词和工具。此前 preset 基础 Plan 已撤下，未实施源码，也未改动会话历史格式；上下文同步所需的格式扩展另在 02e 规划。

## 当前决定：先做提示词与工具

完整 preset 等第二种实际 Agent 模式需要时再考虑。届时机制与定义仍优先放在 xw-agent；现在只集中管理提示词与真实工具集合，让声明和执行使用同一来源。技能正文和资源的按需加载留到后续有实际内容时再设计。

当前不新增 preset 目录、ID、revision、创建协议字段或历史身份，不因预想多场景就扩展 SessionHeader 或增加 RunContext.agent。

“每个 Run 使用一致的配置”不要求“每个 Run 重新解析静态定义”，也不要求“每个 Run 持久化整份提示词”。首期静态部分可在初始化时准备并复用，Run 捕获当前引用；若以后支持更新，再在明确边界切换。历史保存基线与变化、模型生成所需的有效上下文、内存配置生命周期是不同问题；生成需要使用生效指令，不等于每次生成都向历史追加全量配置。

### Codex 源码核对

参考 openai/codex 的 806d9732c974bc8a51b8317c1bd8985544fe627c（2026-10-10），仅作实现参考，不把其复杂能力整体迁入 XiaoWei：

- [会话初始化](https://github.com/openai/codex/blob/806d9732c974bc8a51b8317c1bd8985544fe627c/codex-rs/core/src/session/mod.rs#L760)：base instructions 按显式配置、历史 SessionMeta、模型模板的顺序解析；dynamic tools 在 thread 启动时确定，并可从历史恢复。
- [SessionMeta 写入](https://github.com/openai/codex/blob/806d9732c974bc8a51b8317c1bd8985544fe627c/codex-rs/rollout/src/recorder.rs#L948)：保存基础指令及动态工具定义。这不代表所有内置工具都只在会话初始化时确定。
- [上下文更新](https://github.com/openai/codex/blob/806d9732c974bc8a51b8317c1bd8985544fe627c/codex-rs/core/src/session/mod.rs#L4721)：没有参考基线时注入完整上下文，之后计算变化；TurnContext 仍可按真实用户轮次保存恢复元数据，不能概括成整个历史文件只有配置变化时才写。压缩等导致基线重建时也可能重新注入完整上下文。
- [请求级状态](https://github.com/openai/codex/blob/806d9732c974bc8a51b8317c1bd8985544fe627c/codex-rs/core/src/session/step_context.rs#L23)：StepContext 捕获单次模型请求的不可变设置与实际 ToolRouter，请求之间可以变化；声明和执行共享同一工具计划。
- [请求组装](https://github.com/openai/codex/blob/806d9732c974bc8a51b8317c1bd8985544fe627c/codex-rs/core/src/session/turn.rs#L1563)与[增量工具条件](https://github.com/openai/codex/blob/806d9732c974bc8a51b8317c1bd8985544fe627c/codex-rs/core/src/session/world_state.rs#L43)：普通请求组装路径仍构造含当前基础指令与工具的 Prompt，这描述的是逻辑请求，不能直接推断网络传输量；Responses Lite 且启用增量工具时，通过历史中的基线／变化表达。不能把本地只记一次理解为后续模型请求不再需要相关上下文。

本次未核对 Claude Code 对应版本的实现，不据此断言它采用相同机制。

### 现在与以后实施的成本

当前只有 Quick Chat，未来可以明确将已有无场景身份的会话归到 Quick Chat；晚加身份仍需兼容测试，但没有多种历史来源难以区分的问题。把提示词和工具装配集中在核心，可以控制后来提取 preset 的代码改动范围。

现在做完整框架会立即增加目录／身份／revision、跨层协议、存储兼容与专用测试，而这些抽象还没有第二个场景验证。后做会有一次提取工作，但能按真实的模型、权限、工作区和工具需求确定边界；在保持现有模块边界的前提下，预计总成本更低，无法据现有信息给出可靠工期差值。如果将场景判断散落到 renderer、adapter 和 runtime，未来成本才会明显上升。

## 与 preset 独立的上下文同步决定

用户进一步明确，讨论对象是 harness 如何把能力变化同步给模型，不是网络请求的复用。已确认采用首次／压缩后完整基线、后续变化增量、无变化不追加的规则；首次不按 Run 重置。具体语义、现有 Pi 支持和项目契约缺口统一维护在 [Harness 能力上下文同步](model-types.md#harness-能力上下文同步)。

此前关于完整逻辑请求或 WebSocket 续接的分析不能代替这项要求。harness 负责系统上下文的时间顺序和基线／增量；当前先接提示词与工具，技能后续沿用这一规则。

恢复 preset 工作时，再按第二种模式的真实差异确定身份、会话隔离、权限／工作区、配置更新和持久化范围，不直接恢复之前的完整框架方案。

## 讨论复核：撤回与保留的结论

2026-10-10 用户指出我们只使用 Pi LLM provider，并要求复核此前推导。此次按 XiaoWei 当前接线、已安装 Pi 0.87.1 与上述 Codex 源码复核；以下修订只涉及设计和计划，未实施业务代码。

| 此前结论／推导 | 复核结果与修正 |
| --- | --- |
| 每个 Run 组装并保存一份完整 preset 配置 | 撤回其必要性。把运行使用的配置与静态定义解析、历史注入混在了一起；复用初始化结果即可，无变化不追加系统配置。preset 框架本身也已暂缓。 |
| 每次调用模型仍需提供指令／工具，因此每次要重新注入全量 | 前半句只说明有效上下文必须可用，推不出后半句。已有基线与变化历史持续提供上下文；不按生成次数重新追加全量。 |
| WebSocket 续接、previous_response_id 或缓存能回答基线／增量如何同步 | 撤回其相关性。这些是传输或缓存事实，不能替代 harness 的差异计算、更新记录与上下文重建。 |
| 某些模型不能保留中途系统消息或工具增删，因此需用户选择折叠或拒绝 | 撤回。实际证据是 Pi provider 的默认转换和条件分支，不是目标 API／模型的能力验证；由此引出的兼容策略选择没有充分依据。 |
| 自己组装消息，所以 Pi provider 不会改变语义 | 同样不成立。provider 包内确有折叠与工具集合解析；自有 harness 确定要求，接入层负责验证转换是否满足要求。不能用责任归属抹去实际转换行为。 |
| Pi SystemMessage 字段可直接作为已定的领域／PB 方案，传到 worker 即完成 | 改为待验证的适配候选。现有契约确实缺少有序系统更新，但具体字段不必照搬 Pi；验收应穿过实际 provider，检查最终请求，而非止于 PB 往返或入口 mock。 |
| Codex／Claude Code 足以证明所有指令和工具都只需初始化一次、随后增量 | 不能这样概括。Codex 的上下文差异机制有源码依据，但增量工具有路径条件；Claude Code 本次未核对，不能当作实现证据。 |

仍然有效的决定是：preset 暂缓；harness 采用首次／上下文重建时全量、变化时增量、无变化不追加；先接 tool，再接 skill；工具声明与执行集合保持一致；技能目录与按需加载正文分别处理。此前核对时聊天系统指令为空；当前已通过独立系统记录接入基础正文及实际工具规则，Host 仍只转交请求。具体同步要求统一见 [领域类型](model-types.md#harness-能力上下文同步)，接入验证及限制见[交付证据](implementation-results.md#工具循环与文件工具2026-10-18)。
