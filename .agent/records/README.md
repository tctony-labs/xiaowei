# 开发事项生命周期

`.agent/records/` 在选定 `record + Plans` 路径后，保存非平凡开发事项的 why、what、how，以及当前进展和最终结果。它说明为什么做、做什么、如何做；长期文档则描述当前状态和事实，侧重 what。实施期间可由 active 事项的 `How` 承载当前设计、行为和约束；长期说明可在实施过程中或完成后逐步沉淀到根 `docs/` 或对应包文档，不必等到归档，优先更新已有承载位置。归档前核对并补齐仍需持续维护的说明，没有需要长期维护的内容时，不为归档新增文档。记录不充当逐日开发日志；背景、替代方案和实施结果应与当前说明分开。

## 开发路径选择

开始实施前，Agent 根据需求规模、复杂度和跟踪需要，在以下三条路径中选择；用户已指定时遵循用户选择：

- `record + Plans`：适合较大或复杂的 feature / 需求。record 跟踪整体范围、方案、进展和结果，Plan 跟踪可独立验证的实施切片。
- `Plan`：适合范围较小、方案明确，但需要跟踪多个步骤、依赖或验证的需求。用 Plan 跟踪修改与验证，完成后报告结果并删除 Plan，不要求 record。
- 直接修改：适合简单、局部且可直接验证的任务。无需创建 record 或 Plan，直接修改并验证，按需同步相关长期文档，完成后报告结果与验证结论。

路径按需求的跟踪需要选择，不以 record 是否存在为分流依据。小需求从一开始就可采用 `Plan` 或直接修改，取决于是否需要计划跟踪，无需先提议创建 record，也不强制创建 Plan。

三条路径都可按需在实施过程中及完成后逐步更新长期文档，文档修改遵循根 `AGENTS.md` 的授权规则。同一内容只维护一处；使用 record 或 Plan 时，链接对应文档。

## record + Plans 路径的适用条件与创建

满足以下任一条件时，Agent 优先建议 `record + Plans` 路径：

- 改变架构、模块边界、依赖方向或跨进程协议；
- 改变持久化、安全边界、外部契约或发布方式；
- 存在需要记录的替代方案和长期取舍；
- 需要多个可独立验证的实施切片。

简单的局部 bug 修复、机械调整、文案修改，以及已有 Coding Agent Skill 完整覆盖的例行操作通常可直接修改；需要跟踪多个步骤、依赖或验证时采用 `Plan`。任务在实施中扩大到需要计划跟踪时，可转为 `Plan`；显著扩大到上述范围时，应提出改用 `record + Plans` 路径，并按创建规则补建事项。

新建或补建任何状态的 record 前，必须先向用户说明拟记录的事项和创建理由，获得确认后再创建。用户已明确要求创建该 record 时无需重复确认；仅同意开发或创建 Plan 不等于确认创建 record。已有 record 的维护、状态迁移和文档同步仍按下述规则执行。

## 目录与状态

```text
.agent/records/
├── proposed/
├── active/
└── archived/
```

目录是状态的唯一权威，正文不维护容易漂移的 `Status` 字段：

- `proposed`：正在明确问题、范围和方案，尚未承诺实施；不得创建实施 Plan。
- `active`：已决定推进，仍有实施、必要验收，或明确属于同一目标的后续重大改动；也包括已完成但尚未获用户确认归档的事项。只有尚有实施工作时才为实施切片创建 Plan。
- `archived`：事项已完成，且后续不再基于该事项进行重大改动；或事项被拒绝、放弃、移除、弃用、取代。`Outcome` 必须说明归档原因，取代时链接后继事项。完成归档不表示已交付的功能或决策失效。

常规生命周期为：

```text
proposed → active
proposed → archived  # rejected
active   → archived  # completed / abandoned / removed / deprecated / superseded
```

事项范围已完成并验证，且没有明确属于原目标的后续重大改动时，应提议整理长期说明并归档。成果仍在生效、未来可能修 bug 或继续优化，都不是持续开发该事项的理由。若已交付一个切片，但同一事项仍有后续切片、必要验收或方案调整，则继续留在 `active`，并在 `Current work` 写明剩余工作。

归档必须由用户明确发起，或由 Agent 说明拟归档事项、原因及长期内容的去向，询问并获得用户确认后才能实施。满足完成条件、用户要求开发或同意提交，都不等于授权归档；未获确认时保留在 `active`，完成检查不自动触发状态迁移。用户已明确要求归档该事项时无需重复确认。

归档后的 record 不再修改，包括正文和链接，仅供历史参考，不作为当前设计或行为的依据。

## 命名与移动

- 文件名使用稳定的 `YYYY-MM-DD-kebab-case.md`，日期取事项首次记录日期。
- 状态迁移只移动目录，不修改文件名。
- 移动文档时，在同一次修改中更新未归档文档中的入站链接；归档记录保留原有历史引用。
- `record + Plans` 路径中，实施 Plan 目录必须使用主文档的完整文件名词干。

例如：

```text
.agent/records/active/2026-09-08-dynamic-plugin-loader.md
.agent/plans/2026-09-08-dynamic-plugin-loader/01-loader-baseline.md
```

## 主文档内容

按事项需要使用以下章节，不需要为空章节保留占位：

```text
Why
What
How
Alternatives considered
Current work
Outcome
```

- `Why`：问题、背景和触发条件。
- `What`：目标、范围、非目标和完成标准。
- `How`：方案、边界和约束；实施期间可在此维护当前设计、行为、接口和必要的运维说明。尚未实现的方案应明确标注，避免被当作当前行为；提取到独立文档后，保留关键决策及理由并链接文档，不重复维护当前说明。
- `Alternatives considered`：确实评估过的方案及未采用原因。
- `Current work`：只在 `proposed` 或尚未完成实施的 `active` 事项中使用，
  覆盖更新进展、阻塞和下一步。
- `Outcome`：实施完成或进入 `archived` 前填写实际结果、偏差、
  验证证据和后续事项。

## 实施 Plan

选定 `record + Plans` 路径后，只有正在实施且处于 `active` 时才可以在 `.agent/plans/<initiative-stem>/` 下创建 Plan；选定 `Plan` 路径的任务直接按 [`Plan README`](../plans/README.md) 创建，不为此补建 record。每份 Plan 只覆盖一个可独立验证的实施切片，记录具体文件、执行顺序和验证方法；不要重复主文档中的背景、方案讨论或长期架构说明。

`record + Plans` 路径中，每份 Plan 完成后，应立即把新增的持久决定、实现偏差和验证结论回填主文档的 `How` / `Outcome` 或对应独立文档，再删除该 Plan；不要等整个事项完成后统一清理。

## 生命周期检查

### 进入 active

- Why、范围、非目标和完成标准已经足够明确；
- 关键方案已决定，未决问题不会改变实施方向；
- 创建实施 Plan 时，目录名与事项文件名词干一致。

### 实施完成

- 约定范围已经实现并验证；
- 当前行为、接口和运维方式已经更新到 record 的 `How` 或对应独立文档；
- `Outcome` 已记录实际结果、偏差、验证证据和明确拆出的后续事项；
- 对应 `.agent/plans/<initiative-stem>/` 已删除；
- 判断是否还有明确属于原目标的后续重大改动；没有则向用户提议归档，获得确认后按归档步骤执行，有则在 `Current work` 写明范围，继续留在 `active`。

若必要验收仍属于当前范围，事项仍在实施中。只有明确收窄范围，
并把剩余工作拆成独立后续事项时，才能按收窄后的范围记录实施完成。

### 进入 archived

1. 确认用户已明确发起或同意归档该事项，并说明归档原因。完成归档要求原范围已实现并完成必要验收，不再有基于原事项的重大改动；其他原因包括 rejected、abandoned、removed、deprecated、superseded。
2. 按当前代码核对 `How`，区分需要持续维护的说明与历史信息。跨 package 的说明迁入根 `docs/`，包内部说明迁入对应包目录；优先合并已有文档，不机械复制过时方案、实施流水和验收记录。根 `docs/` 的修改遵循 `AGENTS.md` 的授权规则。
3. record 保留理由、取舍和结果，`How` 链接长期说明；`Outcome` 写明完成情况、验证证据、偏差、未验证边界、归档原因及拆出的后续工作。被取代的事项链接后继事项。
4. 删除对应实施 Plan 和空目录，保持文件名不变，将 record 移入 `archived`。
5. 更新未归档文档中的入站链接：查询历史决策时指向 archived record，查询当前架构或行为时指向长期文档。为长期文档补充所属模块的查阅入口。

没有需要长期维护的内容时，不为归档强制新增文档。归档后冻结 record；常规修复和小调整只更新代码及对应长期说明，新的重大开发事项按创建规则另建 record，不向历史 record 追加进展。

### 内容沉淀示例：桌面日志

| 内容 | 归档时的去向 |
| --- | --- |
| 退出后缺少排障证据、采用 main 统一写入及避免额外 IPC 的取舍 | record 的 `Why`、`How` |
| 日志链路、路径、等级、轮转与保留、TS／Rust／worker 接入边界 | [桌面日志](../../docs/desktop-logging.md)，后续持续更新 |
| cmux 操作、文件查询命令和重启回退 | [manage-dev-instances](../skills/manage-dev-instances/SKILL.md) 及其 reference |
| 实施结果、测试和运行验证、尚未验证的边界、独立后续工作 | archived record 的 `Outcome` |

桌面日志功能仍在使用，但该次建设已结束，不再以原 record 承载后续改动；因此归档，不等待功能被移除或取代。

## 与其他文档的边界

- `.agent/records/`：事项的理由、取舍、进度和结果；实施期间的 `How` 可临时承载当前说明，归档后只作为历史参考。
- 根 `docs/`：跨 package 的架构、接入、完整功能行为和运维说明。
- 对应包目录：包内部的实现与使用说明；README 简述职责、准备与运行入口，详细内容放包内 `docs/`。
- `.agent/plans/`：所选开发路径中正在实施的任务的临时步骤，完成后删除。
- `.agent/skills/`：可重复执行的仓库开发与排障流程，不绑定单个事项。

根与包内长期文档均优先更新已有承载位置；提取后，record 保留理由、取舍和结果，通过链接查阅当前说明，同一内容不重复维护。

后续事项改变已有行为时，应先按跟踪需要选择开发路径；采用 `record + Plans` 路径时，按创建规则获得用户确认后，用新 record 记录这次更改的 why、what、how。三条路径都应同步更新承载该说明的长期文档，实施期间尚未提取的说明更新在对应 active record。不要让多个 record 或文档留下相互矛盾的当前说明，也不要以 archived record 判断当前行为。原事项整体被取代时，按归档规则处理并链接后继事项；不修改已归档 record 的正文或链接。

完成事项时，Git 历史保存被删除 Plan 的执行细节；不要为了保留历史而让已完成 Plan 留在
工作树中。
