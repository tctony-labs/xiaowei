# 部署 XiaoWei 服务器

用户发出“开始部署服务器”等明确指令后执行本流程。该指令授权本次镜像构建、发布及目标环境部署；已明确的目标和操作不重复询问。先汇报目标环境和源码版本，再继续执行。提交、推送或合并源码仍遵循根 [AGENTS.md](../../../AGENTS.md) 的授权规则，不通过部署指令推导 Git 提交授权。

开始前完整读取 [服务端部署文档](../../../server/docs/deployment.md)，核对 [server-image workflow](../../../.github/workflows/server-image.yml) 和实际服务端入口。文件布局、Compose 命令、备份恢复及配置约定以部署文档为准，不在技能中维护第二份。

执行顺序为镜像构建发布 → 生产部署 → 初始化与登录验收 → 运维核对。已有环境复用其配置与数据。查询本地开发实例、重启 Electron 不属于本流程。

## 1. 确定版本并手动构建

- 用户指定源码 ref 时使用该 ref；否则使用远端 develop 的最新已提交版本，记录完整 commit SHA。检查本地未提交的部署相关改动，说明它们不会进入远端构建；若本次部署依赖这些改动，则先报告缺少的提交／推送，不构建一个不含所需修改的版本冒充交付。
- 镜像发布到 GHCR，仅构建、验收和发布 `linux/amd64`；核对目标服务器架构，不增加 arm64 发布流程。
- 服务端镜像通过 `workflow_dispatch` 手动触发，不依赖 push、PR 或版本 tag，不创建 server tag。确认该 workflow 已存在于 GitHub 且支持手动触发；不因远端缺少 workflow 而自行提交或绕过 CI 在生产机编译。
- 构建前确认目标 ref 已具备配置检查入口和本次部署所需能力。当前入口不支持 `--check-config` 时，报告具体阻塞，不用正常启动命令代替检查。

将用户指定 ref（默认 develop）解析为远端完整 `deploy_sha`，核对其所需能力。使用含本流程的 develop 分支作为 workflow ref，传入不可变的源码 SHA；workflow ref 和待部署源码是两个独立概念：

```sh
gh workflow run server-image.yml --repo tctony-labs/xiaowei --ref develop -f source_ref="$deploy_sha"
```

通过 workflow、触发时间、包含源码 SHA 的 run 标题和触发者定位刚发起的 run，记录 `run_id`；不能直接取“最近一次成功构建”。若并发触发导致无法唯一定位，先解决关联关系。run 的 headSha 表示 workflow 所在版本，不能代替 source_ref。最终核对部署包 release.txt 中的源码 SHA、run ID 和镜像 revision 与本次选择一致，不静默部署另一个版本。确定本次临时产物目录 `artifact_dir` 后继续：

```sh
gh run view "$run_id" --repo tctony-labs/xiaowei --json event,headSha,status,conclusion,url
gh run watch "$run_id" --repo tctony-labs/xiaowei --exit-status
gh run download "$run_id" --repo tctony-labs/xiaowei --name server-deployment --dir "$artifact_dir"
```

测试、容器验收和发布全部成功后，从该 run 下载部署包，解压并读取其中的 `image.txt` 和 `release.txt`。部署使用其中的镜像 digest，核对镜像平台和源码 revision；不切换为 latest 或其他 run 的产物。镜像拉取权限不足时处理实际权限问题，不把本机构建产物当作 CI 发布结果。构建失败先定位原因；修复或确认暂时性故障后再重试，不循环触发相同失败。

## 2. 准备配置并部署

核对目标服务器、服务目录、Compose 项目、现有版本和持久数据位置。目标已在当前会话或部署文档确定时直接使用；目标不明确时才询问。只操作本次服务，保留同机其他业务。

先展开对应部署包，按[镜像拉取与版本核对](../../../server/docs/deployment.md#镜像拉取与版本核对)在目标服务器优先从 `ghcr.nju.edu.cn` 拉取本次 CI 发布的准确 digest。完整拉取成功后核对 RepoDigest、linux/amd64 和源码 revision，不把镜像站可访问或 manifest 可读取当作镜像已可部署。镜像站失败时保留旧服务，定位原因后重试或回退 GHCR 原站，仍使用同一个 digest；不使用本机 save／SCP／load 中转，不自行切换未知镜像站或修改全局 Docker 代理、DNS、hosts。

首次部署按模板准备配置；升级时复制现有配置为候选副本，保留用户值，按本次版本的配置变更说明处理新增文件、必填项、改名和删除项。缺少的真实配置由部署者提供，不用占位值绕过校验，不直接用模板覆盖线上配置。保留发布目录内的原始 CI 元信息，按部署文档在候选配置与候选 release.txt 中区分上游镜像和实际拉取引用；备份前不能提前覆盖当前版本的配置或 release.txt。

使用新镜像的临时容器执行 `--check-config`，挂载候选配置，并使用上线时对应的环境变量和文件路径。临时容器不发布业务端口、不启动依赖、不执行数据库迁移；旧服务保持运行。以检查命令的退出码 0 判断通过，不能仅以容器成功创建作为通过依据。

- 配置检查失败：保留旧服务，报告具体文件或字段，修正后重新检查。
- 配置检查通过：首次部署启动依赖和应用；升级按部署文档执行部署包的 `backup.sh`，停止旧应用写入并完成数据库、当前配置、Compose 和镜像版本的配套备份，再切换应用镜像和候选配置。采用单实例原地升级，允许短暂停机。
- 仅保留最近一份升级前回滚备份。新备份成功并完成校验后才替换上一份；备份失败不切换新版本，保留原备份并恢复旧服务。升级失败后的重试继续使用对应的升级前备份，不用失败版本的数据覆盖它。
- 启动后检查 Compose 状态和 readiness 的业务 code。HTTP 200 本身不代表成功。

配置检查只能证明已实现的静态校验通过；数据库连接、迁移和真实外部服务仍需对应的运行验收。新配置文件必须纳入新版本的加载／校验逻辑和部署挂载，不能只放一份模板就认为支持完整。

## 3. 初始化与登录验收

首次部署由用户在服务器配置中填写管理员邮箱和密码，再启动初始化。默认不读取用户密码或登录凭据，不在本机生成或保存管理员凭据，也不执行生产登录、刷新或退出；仅在用户另行明确授权时执行相应认证验收。密码和 token 不进入对话、日志、技能或版本库。

Agent 检查配置、容器健康、初始化记录和公网路由；登录及重建后的会话恢复由用户验证。分别报告技术检查和用户验收状态，不能用健康检查代替登录验收；需要用户验收时，等待其反馈后再宣布完成。CI 中的隔离账号与自动认证测试继续执行，不使用生产账号。

保留 `.env` 的两项初始化变量和“仅首次初始化使用”的注释，不在部署收尾时自动移除或改写其值。已有初始化标记时，这些变量不会重置密码或创建第二个管理员；升级保留现有配置与账号。清库重新初始化不属于普通部署、升级或失败重试，只有用户明确要求重置数据时才按部署文档处理。

## 4. 运维与交付

核对备份文件、镜像与配置版本对应关系、日志和轮转，以及升级与回滚步骤。只有升级或回滚验收通过后才删除 `backups/upgrade-pending`；失败重试不得移除此标记。升级成功后仍保留该回滚备份，直到下一次有效的升级前备份替换它；不增加定时备份或历史备份保留。恢复演练使用隔离数据库，不覆盖生产库。上线失败时先确认数据库迁移状态及兼容性，按部署文档恢复匹配的版本与配置；需恢复数据库时使用本次升级前备份，不能假定换回旧镜像即可回滚。若新版本已接受业务写入，先说明恢复将丢失的数据范围并取得确认。

最后报告部署 URL、源码 SHA、CI run 链接、上游镜像及实际拉取引用、验收结果和未完成项。清理本次临时容器与验收会话，保留运维所需的发布材料和备份；部署结果仅在对话中报告，不写入开发 record，也不为例行部署新建 record。服务器保留 release.txt 和发布材料供运维核对；本地下载和验收产物使用临时目录，完成后清理，不自行建立长期部署记录目录。
